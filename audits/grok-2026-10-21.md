## Threat model (STRIDE)

The package is the handler a site mounts at `/api/carrel/v1` so Carrel, and a site's own admin, can list, edit, and publish that site's content. The site supplies a `SiteAdapter`. One bearer key per site (`CARREL_SITE_KEY`) opens every route. The content kit (`src/admin`) is a second gate, per person, and only when the caller goes through the kit. The package holds no database. The thing it can lose is a check that stores active SVG, a tag write a YAML reader will not round-trip, or a workflow token that can push.

Who can call it: any site that imports the modules, anyone who holds that site's key, a person using the kit with the permissions the host passed in, and GitHub Actions on pull request, push, a `v*` tag, a Monday cron, and `workflow_dispatch`.

Entry points:

- One HTTP handler, `createSiteApi`. Routes under the prefix for meta, content (including tags, revisions, diff, delete), preview, and, when the adapter offers them, media and mentions. Unknown paths inside the prefix are 404 after the key. Paths outside the prefix are 404 before the key.
- Library: `createSiteClient`, `localClient`, the frontmatter readers and writers, `runConformance`, `memoryAdapter`, and the kit intent runners.
- Workflows: `ci.yml` (every push and every pull request), `ai-author.yml` (pull request, and push to `main`), `pr-footer.yml` (pull request), `code-map.yml` (push to `main`, cron `37 4 * * 1`, dispatch), `bump-consumers.yml` (tag `v*` and dispatch).
- No MCP server, queue, webhook, or cron inside the library. The Monday cron is GitHub Actions.

Where trust changes:

- The prefix check runs first. A path outside it never reaches the limiter or the key.
- The rate limiter runs next, keyed by `CF-Connecting-IP` or the literal `unknown`. A limiter that throws is a 503.
- A configured key shorter than 32 characters is a 503 before any compare.
- The bearer is compared as a SHA-256 digest (SA-9).
- The route runs only after that. Zod parses the body and the query. `checked()` parses what the adapter returns.
- The adapter is the site. This package trusts it to store bytes and to render preview HTML.
- The kit refuses an intent the person may not run before it calls the site. The raw API does not apply those permissions. One key can delete, sweep, and empty trash. The README says so.
- Caller commands in the pinned devkit code-map job run as shell in a job whose token can push (SA-3).

Spoofing: the compare is of digests. A short configured key fails closed. An empty presented key is 401. Two empty strings compare equal inside `keysMatch` itself (SA-9). The route's length floor runs first.
Tampering: `main` is unprotected (SA-3). Content, tags, mentions, and media metadata writes carry a version. Media delete does not. An upload whose type the site did not declare is refused before the body is read. An SVG the signature accepts can still carry a script (SA-1).
Repudiation: `changeId` is stored on the write the adapter performs. This package does not keep its own audit log.
Information disclosure: refusal logs name a reason (`wrong-key`, `no-key`, `rate-limited`) and do not log the key. Preview HTML is the adapter's string, returned as `text/html` with `no-store` and `nosniff`. The code-map job still has the GitHub token in the measure steps (SA-3).
Denial of service: bodies stop at 4 MB via `readCapped`. Uploads stop at the site's `maxBytes`. The rate limiter is the site's binding. A missing `CF-Connecting-IP` shares the bucket `unknown`.
Elevation: the kit's permission checks are what stop an editor from publishing. Breaking them makes the kit tests go red. The API key is above that gate by design. An editor who may edit and may not publish can still upload an SVG the signature calls valid (SA-1).

## Findings

### SA-1 MAJOR, security, confirmed by running

Files: `src/media.ts` lines 64-68 and 72-81, `src/testing.ts` lines 51-54, `src/server/media.ts` lines 47-58.

`checkUpload` is the byte check the upload route runs before `media.upload`. For `image/svg+xml` the signature is: no NUL in the first 4096 bytes, an optional BOM, a `<` near the start, and `/<svg[\s>]/i`. This input returned `null` from `checkUpload`, and `POST /api/carrel/v1/media?filename=x.svg&changeId=c1` with `content-type: image/svg+xml` returned 201. The memory adapter stored `uploads/1-x.svg`, content type `image/svg+xml`, 54 bytes:

```html
<svg onload="alert(1)"><script>alert(1)</script></svg>
```

`MEMORY_MEDIA_LIMITS` includes `image/svg+xml`, so the reference adapter and any site that copies those limits will store it. The package does not serve `/media/`. The site that later responds to that URL as `image/svg+xml` on its own origin is where the script runs. An editor whose kit permissions include `edit` and exclude `publish` can upload. The kit treats upload as an edit.

The same signature function accepts a buffer that starts with `%PDF-` and contains `/JS`. `MEMORY_MEDIA_LIMITS` does not include `application/pdf`. A site that adds that type gets the same class of hole. It is part of this finding.

`<svg/onload=...>` does not match `/<svg[\s>]/` and is refused. The tests refuse an SVG only when the site did not declare that type.

Path: an editor, or anyone who holds the site key, uploads the SVG. The route's type check passes because the site listed the type. The signature passes because an `<svg` element is present and there is no NUL. The adapter stores the bytes. A page on that origin that loads the file as an image, or a visitor who opens the file URL, runs the script if the response is `image/svg+xml`.

Smallest fix: refuse an SVG whose head contains `script`, an `on` handler, `javascript:`, or `foreignObject`, or drop `image/svg+xml` from `MEMORY_MEDIA_LIMITS` until the bytes are sanitized. Apply the same refusal to a PDF whose head contains `/JS` or `/JavaScript` when the site accepts `application/pdf`.

### SA-2 MAJOR, correctness, confirmed by running

Files: `src/contract/content.ts` line 9, `src/frontmatter.ts` lines 88-89.

`ContentTag` is 1 to 40 characters and excludes whitespace, commas, brackets, quotes, `#`, `:`, and backslashes. It accepts `no`, `true`, `n`, `on`, `yes`, `*`, and `{`. `setTags` writes the list unquoted:

```ts
return setRawKey(front, "tags", `[${tags.join(", ")}]`);
```

The probe wrote `tags: [no]`, `tags: [true]`, `tags: [*]`, and `tags: [{]`. A YAML 1.1 parser reads `no`, `n`, `yes`, `on`, and `true` as booleans. `*` and `{` can make the document invalid. A YAML parser was not executed in this audit. The package's own `tagsOf` splits the text and still returns the word, so `test/content-tags.test.ts` can lock `tags: [News, Field notes]` and stay green.

Path: `PUT /content/:id/tags` with one of those tags, or the kit's `tag-add`, which calls the site's `setTags` or the frontmatter fallback. The post source now contains a tag the schema accepted and a YAML 1.1 reader will not give back as that string. The site's render is the next step.

Smallest fix: `JSON.stringify` each tag inside the flow list. `readList` already `JSON.parse`s a double-quoted item.

### SA-4 MINOR, correctness, confirmed by running

File: `src/frontmatter.ts` lines 23-33, 66-69, and 93-115.

`blocks()` splits on `\n` only. `KEY` is `^([A-Za-z_][\w-]*):(.*)$`, so a CR stuck to the value fails the key match for the next reader and still rides along inside the line.

Probe input:

```text
---\r\ntitle: Hello\r\ntags: [old]\r\n---\r\nBody\r\n
```

`splitSource` returned the front `title: Hello\r\ntags: [old]`. `readKey(front, "title")` returned `""`. `tagsOf` still found `old`, because the tags line had no CR of its own after the split. `setTags` replaced the tags block and left the CR on the title line. `setRawKey(front, "title", '"Hi"')` produced a second title:

```text
title: Hello\r\ntags: [old]\ntitle: "Hi"
```

`test/frontmatter.test.ts` round-trips CRLF by split and join. It does not call `readKey` on a line that still contains CR.

Path: a post whose source uses CRLF, then a kit write that sets the title or the tags. The title reads back empty, and a title write appends a second key. A YAML parser that keeps the first key still shows `Hello`.

Smallest fix: strip `\r` in `blocks()` before matching keys, and add a test that calls `readKey` and `setRawKey` on a CR line.

### SA-8 MINOR, reliability, confirmed by reading

File: `src/server/media.ts` lines 140-152.

Empty-trash gathers ids, then deletes them one at a time. A `refused` or `not-found` error is recorded in `refused` and the loop continues. Any other error is rethrown. The route's catch turns that into a 500. `deleted` never reaches the client, and the ids already removed stay removed.

Path: a trash of several files, and the adapter throws an internal error on the second delete. The caller sees 500 and cannot tell which ids are gone. A retry starts again from whatever is still trashed.

Smallest fix: record the internal failure on that id, stop the loop, and return 200 with `deleted`, `refused`, and the error on the id that stopped it. The client can retry the rest.

### SA-9 MINOR, security, confirmed by running

File: `src/server.ts` lines 52-58. Compare with `@dustinedwards/site-runtime` `safeEqual` at the installed `v0.7.0`.

`keysMatch` hashes both sides with SHA-256 and then uses `crypto.subtle.timingSafeEqual` when that function exists, otherwise a XOR loop. `safeEqual` returns false when either side is empty or not a string. `keysMatch("", "")` returned `true` on this machine. `keysMatch("", "a")` returned `false`.

The handler calls `keysMatch` only after `expected.length < MIN_KEY_LENGTH` (32) has already returned 503 (`src/server.ts` lines 99-107). The route is safe. The exported function is the drift the shared compare was written to end. Node v24.21.0 on this machine has no `timingSafeEqual` on `crypto.subtle`, so the handler takes the XOR loop. The plant that forces `return diff === 0` to `return true` turned wrong-key requests into 200.

Smallest fix: call `safeEqual` and keep the 32-character floor in the handler.

### SA-10 MINOR, tests, confirmed by reading

File: `src/conformance.ts` lines 397-406.

The stale-mention check loads the first mention, POSTs `decide` with `expectedVersion` set to `carrel-conformance-stale-version`, and requires status 409 and error code `version-conflict`. It does not read the mention again. A site can apply the reject and still return 409. The probe reports a pass.

The unknown-id probes use ids and versions no site should hold, and they check the error code. This one is the check that has a real id in hand and does not look at the row afterwards.

Smallest fix: GET the mention after the 409 and require the same version and status as before the call.

## Area by area

### 1. Security

Credential table:

| Credential | Where it lives | Who can read it | What a leak opens | Rotation |

Checked and clean, apart from SA-1, SA-3, and SA-9:

- Order. Prefix, then rate limit, then key length, then digest compare, then route (`src/server.ts` lines 85-118). A missing key is 401 for every in-prefix path, including unknown routes. A path outside the prefix is 404 with no key check. The planted tests assert the adapter was not called.
- Injection. There is no SQL, no shell, and no `eval` in `src`. Ids are zod regexes (`ContentId`, `MediaId`, `ChangeId`). Preview HTML is the adapter's string, not a template this package builds. The memory adapter's preview escapes title and source (`src/testing.ts` line 479). The handler copies the adapter string through with `content-type: text/html` (`src/server/content.ts` lines 151-158).
- Headers. `BASE_HEADERS` is `cache-control: no-store` and `x-content-type-options: nosniff` (`src/server/http.ts` lines 27-30). No CORS header, so a browser on another origin does not get a cross-origin read. No CSP on the preview response. The site's own document policy is what covers a preview navigation. HSTS is the site's header, not this library's.
- CSRF. The credential is a bearer header. There is no cookie session.
- Authorization. The kit checks `edit`, `publish`, `deleteContent`, `deleteMedia`, and `decideMentions` before the site call. Breaking the posts permission line and the live-post line each turned `test/admin.test.ts` red (area 11). The raw API is one key for every route. The README states that, and the kit is the per-person layer.
- Upload bound. The type is checked with `bytes === null` before `readUpload` (`src/server/media.ts` lines 50-54). `test/body-limit.test.ts` cancels a stream at the limit and asserts the adapter was not called.
- Rate limit. A limiter throw is 503, logged as `limiter-failed`, and the route does not run. `localClient`'s limiter always returns success. The comment and the README say the site's own sign-in guards that door.
- Cryptography on the route. Digests are 32 bytes. The XOR loop visits every byte. The length floor rejects a short configured key before the compare.
- `CF-Connecting-IP`. On a Worker, Cloudflare sets that header. A request that arrives without it shares the bucket `unknown`. The package does not implement the counter. The site passes the binding.

Media delete takes `changeId` and does not take `expectedVersion` (`src/server/media.ts` lines 73-77). That is the written contract. A reused id can delete the file that now holds that id. Callers who need a version check have the metadata writes, which do take one.

### 6. Reliability

Checked and clean, apart from SA-8:

No Workers CPU alarm lives here. The site that mounts the handler owns the isolate limits. A 4 MB JSON body is the largest single request this package will read.

### 7. Performance and cost

No D1 database, so no `EXPLAIN QUERY PLAN`.

Worst case for one request: a body of 4 MB, parsed as JSON, then an adapter call. Upload reads at most `limits.maxBytes` after the type check. List endpoints pass the query to the adapter. There is no N+1 in the handler except empty-trash, which is one list page loop and then one delete per id, capped. Preview is one adapter render.

The code-map job on a push runs the whole test suite with coverage. The Monday job also runs four Stryker chunks (`contract`, `server`, `admin`, `rest`) with a 120 minute timeout. That is the expensive cron. It is weekly, and it is the run that refreshes `mutation.json`.

The published map reports one cycle, `src/client.ts` and `src/local.ts`. `local.ts` calls `createSiteClient` inside the function, and `client.ts` re-exports `localClient`. The cycle loads.

Caching: API responses send `cache-control: no-store`. The GitHub `code-map` files send GitHub's `max-age=300`. That cache is GitHub's, not this package's.

### 10. Architecture and simplicity

The real structure: a site builds an adapter, mounts `createSiteApi` at `/api/carrel/v1`, and puts the key in the environment. Carrel uses `createSiteClient` over HTTPS. The site's own admin uses `localClient` over the same handler in process, then the kit. Frontmatter is a separate export so an editor can rewrite a block without a YAML parser. Conformance and the memory adapter ship so a site can test itself. Workflows call devkit. There is no second HTTP framework and no database.

The README describes that shape. The code matches it. The one cycle in the published map is the client/local pair, and it is a deferred call.

Over-engineering: the contract is split across `src/contract/*.ts` plus a barrel, and three fixture generations. That cost is what keeps old callers compiling. I would not delete it.

Under-engineering: the SVG signature is a regex where a sanitizer belongs (SA-1). The tag writer is string join where quoting belongs (SA-2). The compare is a local copy where `safeEqual` belongs (SA-9).

Shared code: `readCapped` is correctly imported. `keysMatch` should not remain local. Nothing else in `src` is a second copy of devkit, site-runtime, d1-dump, or capsomer.
